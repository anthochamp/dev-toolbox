# Ansible Role & Collection Authoring

## Core Principles

1. **Generic & Publishable** — Roles work in any infrastructure, Ansible Galaxy ready
2. **Respect Tool Philosophy** — Variable names and structures mirror the tool's native configuration format
3. **Self-Contained** — No external dependencies or references to project-specific paths
4. **Idempotent** — Safe to run multiple times in any state
5. **Check Mode Compatible** — Support `ansible-playbook --check`
6. **Loosely Coupled** — Roles are independent; place shared content in a dedicated "common" role

## Role Structure

### Directory Layout

Use the standard Ansible role structure generated by `ansible-galaxy init`:

```
roles/<category>/<role>/
├── README.md
├── defaults/main.yml    # User-overridable variables
├── vars/                # OS-specific internal variables (not user-configurable)
│   ├── Debian.yml
│   └── RedHat.yml
├── tasks/main.yml
├── handlers/main.yml
├── templates/           # Jinja2 templates (.j2)
├── files/               # Static files
└── meta/main.yml        # Galaxy metadata and dependencies
```

### Role Design

- Design the interface focused on **functionality**, not the software implementation behind it
- Do not hardcode host group names in roles — make group names parameters with defaults
- Validate role arguments early using `assert` module or argument specs; fail early with clear error messages
- When using `include_tasks` or `import_tasks`, prefix task names for clarity: `"Apache: Install packages"`
- Package roles in an Ansible collection to simplify distribution and consumption

### Check Mode and Idempotency

- Ensure roles support `--check` mode:
  - Templates: `validate: 'tool --check %s'`
  - Commands: `when: not ansible_check_mode`
- Use `changed_when` for all `command`/`shell` tasks
- Use handlers for service reloads only — tasks must not make changes if already in desired state

### Multi-Distribution Support

- Support multiple OS distributions when applicable
- Use platform-specific variables (`vars/{{ ansible_os_family }}.yml`) for OS facts
- Use platform-specific tasks (`tasks/{{ ansible_os_family }}.yml`) when needed, included with `include_tasks`

### Templates

- Use `template` module over `copy` for configuration files; append `.j2` to template file names
- Keep filenames close to destination system names
- Break lengthy Jinja templates into multiple templates for distinct logical sections
- Jinja templates should produce text and semi-structured data, not structured data
- Prefer filter plugins over Jinja templates for data manipulation

### Vars vs Defaults

- Use `defaults/main.yml` for variables users are expected to override
- Use `vars/main.yml` for internal role variables that should not be overridden
- Variables in `vars/` have higher precedence than `defaults/`

## Tool Philosophy: No Custom Abstractions

**Rule:** Variable names and structures must mirror the tool's actual configuration format.

**Bad Example** — Custom abstraction:

```yaml
service_web_ports: [80, 443]  # Made-up abstraction
service_db_access: "10.0.0.0/8"
```

**Good Example** — Direct mapping to tool's config:

```yaml
# Mirrors actual nftables syntax
firewall_input_rules:
  - "tcp dport { 80, 443 } accept"
  - "ip saddr 10.0.0.0/8 tcp dport 3306 accept"
```

**Why:** Users can directly reference the tool's official documentation without mental translation.

## Variable Naming

**CRITICAL RULE:** Variable names must mirror the tool's actual configuration options.

**Single values:** `<namespace>_<category>_<option_name>`

```yaml
# Variable name             →  Config file option
service_db_bind_address        →  bind-address
service_db_max_connections     →  max_connections
service_db_buffer_pool_size    →  buffer_pool_size
```

**Object values (ONLY when sharing common prefix):** `<namespace>_<prefix>: { <suffix>: value }`

```yaml
# All config options share innodb_ prefix
service_innodb:                  →  innodb_buffer_pool_size
  buffer_pool_size: "1G"         →  innodb_log_file_size
  log_file_size: "256M"          →  innodb_file_per_table
  file_per_table: true
```

**Collections:** `<namespace>_<items>: [ {...}, {...} ]`

```yaml
# Variable structure          →  Config file
service_pools:                  →  pool "name" { ... }
  - name: "data"                     pool "cache" { ... }
    driver: "zfs"
```

Additional naming rules:

- Use valid Python identifiers in `snake_case_naming_schemes`; no special characters other than underscore
- Pattern `object[_feature]_action` guarantees proper sorting
- Avoid abbreviations; use capital letters for abbreviations where unavoidable
- Prefix internal OS-specific variables with `_` (e.g., `_service_packages`) to signal they are not user-configurable

**Why:** Users reference official documentation without translation.

## Variable Structure Patterns

Choose the right structure based on how options relate in the tool's configuration.

### Single Value Variables

**When to use:** Values are **independent and unrelated** in the config file or command line.

```yaml
service_port: 8080
service_bind_address: "0.0.0.0"
service_max_connections: 100
service_timeout: 30
```

### Object Value Variables

**When to use:** Options **share a common prefix** in the actual config file.

**CRITICAL RULE:** Only nest variables when they ALL start with the same prefix in the tool's config.

**✅ GOOD — Common prefix `innodb_`:**

```yaml
service_innodb:
  buffer_pool_size: "1G"      # innodb_buffer_pool_size
  log_file_size: "256M"       # innodb_log_file_size
  file_per_table: true        # innodb_file_per_table
```

**✅ GOOD — Common prefix `tls_` in HCL:**

```yaml
service_listener:
  address: "0.0.0.0:8200"     # address (no prefix)
  tls:
    disable: false            # tls_disable
    cert_file: "..."          # tls_cert_file
    key_file: "..."           # tls_key_file
```

**❌ BAD — Mixed prefixes (`ssl_`, `tls_`, no prefix):**

```yaml
# DO NOT DO THIS — these don't share a common prefix!
service_tls:
  cert: "..."               # ssl_cert (not tls_cert!)
  key: "..."                # ssl_key (not tls_key!)
  version: "TLSv1.2"        # tls_version (different prefix!)
  require: false            # require_secure_transport (no prefix!)
```

**Correct (flat variables):**

```yaml
service_ssl_cert: "..."
service_ssl_key: "..."
service_tls_version: "TLSv1.2"
service_require_secure_transport: false
```

### Collection Variables

**When to use:** Multiple **instances of the same configuration pattern**.

```yaml
service_firewall_rules:
  - "tcp dport 80 accept"
  - "tcp dport 443 accept"
  - "ip saddr 10.0.0.0/8 tcp dport 3306 accept"

service_storage_pools:
  - name: "data"
    driver: "zfs"
    path: "/pooldata"
  - name: "cache"
    driver: "lvm"
    path: "/poolcache"
```

## Default Values

**CRITICAL RULE:** Role defaults must match the tool's actual defaults.

**Exception:** Use secure/modern defaults when the tool's defaults are kept for backward compatibility.

**✅ GOOD — Match tool defaults:**

```yaml
service_port: 3306                  # Tool's default port
service_max_connections: 151        # Tool's default
service_connect_timeout: 10         # Tool's default
```

**✅ GOOD — Override insecure/legacy defaults (always document why):**

```yaml
# Listening Address
# Purpose: IP address to bind to
# Default: MariaDB default is "*" (all interfaces)
# Security: localhost-only by default, expand after TLS configured
# References:
#   - MariaDB: https://...
service_bind_address: "127.0.0.1"
```

## Package and Path Management

**CRITICAL RULE:** Roles know their own packages. Users should NOT specify them.

### OS-Specific Variables (vars/)

Packages and paths are **OS facts**, not user configuration.

```yaml
# vars/Debian.yml
---
# OS-specific facts for Debian/Ubuntu — not user-configurable

_service_packages:
  - service-daemon
  - service-client
  - python3-service-lib

_service_name: "service"
_service_config_file: "/etc/service/service.conf"
_service_data_dir: "/var/lib/service"
_service_user: "service"
_service_group: "service"
```

```yaml
# vars/RedHat.yml
---
_service_packages:
  - service              # Different package name
  - python3-ServiceLib   # Different Python package

_service_config_file: "/etc/service.conf"  # Different path
```

```yaml
# tasks/main.yml
- name: Include OS-specific variables
  include_vars: "{{ ansible_os_family }}.yml"

- name: Install packages
  package:
    name: "{{ _service_packages }}"
    state: present

- name: Configure service
  template:
    src: service.conf.j2
    dest: "{{ _service_config_file }}"
  notify: Restart service
```

### Optional Packages

Only expose packages when users have **valid choices**:

```yaml
# defaults/main.yml
service_optional_packages: []
  # - service-plugin-monitoring
  # - service-plugin-authentication
```

## Privilege Escalation

Use `become: true` for: packages, system files (`/etc/*`), services, and firewall rules.

## Documentation

### defaults/main.yml Format

```yaml
# =============================================================================
# Section Name (corresponds to config file section)
# =============================================================================

# Variable Name
# Purpose: What this option controls
# Example:
#   variable_name: "example_value"
# Performance/Security Note: When relevant
# References:
#   - Tool Docs: <official documentation URL>
#   - Man Page: <man page reference>
variable_name: "default_value"
```

### README Structure

Every role MUST have a `README.md` covering:

- Purpose (one paragraph)
- Requirements (OS, Ansible version, dependencies)
- Variables (concise table)
- Example playbook
- License

For roles with extensive configuration, use a `docs/` subdirectory following the Diátaxis framework:

```
roles/<category>/<role>/
├── README.md              # Quick reference
└── docs/
    ├── how-to/            # Task procedures
    ├── explanation/       # Design rationale
    └── reference/         # Detailed configuration reference
```

Use a `docs/` subdirectory when **any** of the following apply:

| Condition | Example |
| --- | --- |
| More than 3 logical configuration sections | `[server]`, `[tls]`, `[storage]`, `[auth]`, ... |
| Non-obvious setup requiring step-by-step procedures | Multi-step PKI bootstrap, cluster join |
| Design decisions that need rationale | Why mutual TLS is enforced; why a specific scheduler was chosen |
| Reference material that would make `README.md` > ~150 lines | Full variable table, all enumerated values |

Otherwise, a single `README.md` is sufficient.

### Cross-Referencing Rule

**❌ Roles CANNOT reference project docs:**

```markdown
<!-- FORBIDDEN in role README -->
See ../../docs/architecture.md for network topology
```

**✅ Project docs CAN reference roles:**

```markdown
<!-- OK in docs/reference/database.md -->
See ansible/roles/services/database/README.md for role details
```

**Why:** Roles must be self-contained and portable.

## Site-Specific vs Generic

**Roles must be generic.** Site-specific details belong in inventory.

### Bad Example: Site-Specific in Role

```yaml
# roles/vpn/defaults/main.yml
vpn_server_address: "vpn.example.com"  # Hardcoded domain
vpn_client_network: "10.50.0.0/16"     # Specific network
vpn_peers:
  - name: "headquarters"               # Specific site name
    endpoint: "hq.example.com:51820"
```

### Good Example: Generic Role

```yaml
# roles/vpn/defaults/main.yml
vpn_server_address: ""    # User configures
vpn_client_network: ""    # User configures
vpn_peers: []             # User provides list
```

Site-specific configuration belongs in inventory `host_vars/` and `group_vars/`. Architectural decisions belong in project `docs/explanation/`.
